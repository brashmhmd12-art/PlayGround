# المراجعات قبل التنفيذ (Security / UX / Testing Review)

## 1. مراجعة أمنية ذاتية للتصميم (نقاط ضعف وجدتها وحلها)

1. **خطر: الاعتماد على إخفاء زر الإدارة.** الحل المعتمد: لا قيمة للإخفاء
   أمنيا؛ الحماية = فحص الدور خادميا على كل مسار + اختبار اقتحام بمحاولة
   دخول طالب للوحة (مذكور في مصفوفة الاختبار).
2. **خطر: تسرب الإجابات عبر المراجعة.** إذا سمح `allow_review` مع عرض المفاتيح،
   طالب ينهي مبكرا يخبر زملاءه. الحل: خياران منفصلان (إظهار الدرجة / إظهار
   الإجابات) + عدم عرض المراجعة قبل انتهاء نافذة الامتحان للجميع (خيار افتراضي).
3. **خطر: التوقيت المعتمد على العميل.** الحل: ساعة الخادم + deadline ثابت +
   رفض الحفظ المتأخر + تسليم تلقائي بمهمة مجدولة (وليس بانتظار طلب الطالب).
4. **خطر: التزامن (نقر مزدوج/تحديث أثناء التسليم).** الحل: Idempotency-Key +
   قيد فريد + معاملة واحدة (مفصل في وثيقة قاعدة البيانات).
5. **خطر: ثقة عمياء بمحتوى المشرف (XSS مخزن عبر سؤال/شرح).** الحل: تعقيم
   كل HTML معروض أيا كان مصدره + CSP.
6. **خطر: حذف بالخطأ يفقد بيانات.** الحل: حذف ناعم + نسخ احتياطي مُختبر.
7. **خطر: تغيير سؤال بأثر رجعي.** الحل: لقطات النسخ في المحاولة.
8. **خطر متبقٍ معلن: مشاركة الحسابات بين الطلاب.** التخفيف: جلسة امتحان
   واحدة نشطة + سجل أجهزة + تنبيه عند الدخول من جهاز جديد. المنع الكامل
   يتطلب مراقبة بشرية وهو خارج نطاق البرمجيات.

## 2. مراجعة تجربة الاستخدام (UX)

- واجهة الطالب أثناء الامتحان: أبسط شاشة في النظام (سؤال واحد بارز، خريطة
  مصغرة، عداد واضح، زر تسليم بتأكيد مزدوج). لا عناصر مشتتة.
- رسائل الخطأ عربية واضحة مع إجراء (مثال: انقطاع الإنترنت = "يتم الاحتفاظ
  بإجاباتك محليا وستُزامن تلقائيا" لا مجرد "خطأ").
- إمكانية الوصول: تباين ألوان، أحجام خطوط، عمل كامل بلوحة المفاتيح،
  استجابة للهاتف أولا.

## 3. مراجعة الاختبارات (مصفوفة الإطلاق الإلزامية — من قسم 36)

| الاختبار | النجاح المتوقع |
|---|---|
| طالب يطلب مسارا إداريا | رفض 403 + تسجيل في التدقيق |
| تعديل النتيجة من العميل | تُتجاهل القيمة ويُعاد الحساب خادميا |
| تسليم مزدوج متزامن | سجل نتيجة واحد فقط |
| انتهاء الوقت أثناء الإجابة | تسليم تلقائي ورفض أي حفظ بعده |
| انقطاع الإنترنت ثم العودة | مزامنة بـ seq بدون فقدان أو تكرار |
| تحديث الصفحة أثناء الامتحان | استئناف بنفس deadline |
| فتح الامتحان من جهاز آخر | استئناف نفس المحاولة، لا محاولة جديدة |
| تعديل سؤال بعد بدء الامتحان | المحاولات القائمة على اللقطة القديمة |
| الوصول لامتحان غير منشور | 404/403 حسب الحالة |
| الوصول لنتيجة طالب آخر | 403 + تسجيل |
| SQLi / XSS / CSRF / Brute Force / تصعيد صلاحيات | كلها مرفوضة ومُسجلة |
| تعديل يدوي لعلامة | سجل old/new + السبب + الفاعل |

لا يعتبر المشروع جاهزا قبل اجتياز كامل المصفوفة على بيئة staging.

## 4. القرار المطلوب منك قبل كتابة الكود

التصميم أعلاه محايد بين مسارين للتنفيذ، وأحتاج اختيارك:

- **(أ) المسار السريع الإنتاجي: Supabase.** أنشئ مشروعا مجانيا، وأزودك
  بملفات الترحيل (Migrations) والسياسات (RLS) والدوال، وأعيد بناء الواجهة
  لتتكلم مع الخادم الحقيقي. المدة أقصر ولا خادم تديره.
- **(ب) المسار الكامل: NestJS + PostgreSQL.** تحكم مطلق وعبء تشغيلي
  (خادم دائم، أسرار، نسخ، مراقبة) — مبرر فقط عند التوسع لمدارس/مدرسين.

توصيتي المهنية: ابدأ بـ (أ). صُمم كل شيء (الأدوار كقدرات، اللقطات،
المعاملات) بحيث الانتقال إلى (ب) لاحقا لا يتطلب إعادة تصميم.
