# معمارية النظام (System Architecture)

## 1. المبدأ الحاكم

الواجهة الأمامية (Frontend) ليست مصدر ثقة إطلاقا. كل قرار مؤثر (الصلاحيات، الوقت،
حالة الامتحان، صحة الإجابة، العلامات، التسليم، الوصول للنتائج) يتحقق منه الخادم
(Backend) ضد قاعدة البيانات. الواجهة تعرض فقط ما يسمح به الخادم.

نتيجة مباشرة: النسخة الثابتة الحالية على GitHub Pages (ملف واحد + تخزين محلي)
لا يمكنها تحقيق هذا المبدأ، وهي بذلك نموذج عرض فقط، وليست النظام الإنتاجي
المطلوب هنا. النظام الإنتاجي يتطلب المكونات أدناه.

## 2. المكونات

```
+-------------+      HTTPS      +----------------+      SQL      +------------+
|  Frontend   | <------------> |    Backend     | <----------> |  PostgreSQL |
| (Static SPA)|   JSON + JWT   |  (API + Jobs)  |              | (RDS/Supabase)|
+-------------+                +----------------+              +------------+
        |                               |
        |                               +--> Object Storage (صور الأسئلة/الملفات)
        |                               +--> Queue (إشعارات، تصحيح، نسخ احتياطي)
        |                               +--> Audit Log (جدول + تخزين غير قابل للتعديل)
```

## 3. اختيار التقنية المقترح (مع التبرير، لا للشهرة)

### الخيار الموصى به أولا: Supabase (PostgreSQL مُدار) + واجهة ثابتة

| المتطلب | كيف يغطيه |
|---|---|
| PostgreSQL حقيقية، علاقات، فهارس، معاملات | نواة Supabase نفسها |
| مصادقة آمنة + كلمات مرور مُجزأة (bcrypt) + جلسات + 2FA للمشرف | Supabase Auth جاهز ومُدقق |
| تحقق من الصلاحيات Server-Side | سياسات RLS على مستوى الصف + Edge Functions للعمليات الحرجة (التسليم، التصحيح) |
| حماية Brute Force وRate Limiting | مدمجة في Auth وقابلة للضبط |
| نسخ احتياطي يومي + استعادة | مدمجة |
| لا أسرار في الواجهة | مفاتيح النشر علنية بالتصميم، ومفتاح الخدمة يبقى في الخادم فقط |
| كلفة وتشغيل لمعلم واحد | طبقة مجانية كافية للبداية، ولا خادم تديره بنفسك |

لماذا لا NestJS ذاتي الاستضافة كخيار أول؟ لأنه يتطلب خادما دائما، وإدارة أسرار،
ونسخا احتياطيا، ومراقبة — عبء تشغيلي غير مبرر لحجم الاستخدام (معلم + طلاب صف).
ننتقل إليه فقط إذا تجاوزت الحاجة (مدرسون متعددون، دفع إلكتروني، منطق معقد).

### الخيار الثاني (عند التوسع): NestJS + PostgreSQL على Render/Railway

مبرره الوحيد: تحكم كامل في المنطق والطوابير والمهام الخلفية عندما تتجاوز
المتطلبات ما توفره الدوال الجاهزة. كلفته: خادم دائم + DevOps.

## 4. حدود الثقة (Trust Boundaries)

1. المتصفح: غير موثوق. أي قيمة تأتي منه (وقت، علامة، دور) تُعاد حسابها في الخادم.
2. شبكة الإنترنت: تُفترض معادية (التقاط، إعادة إرسال) — لذلك HTTPS إجباري،
   ومعرفات عدم التكرار (Idempotency-Key) لكل عملية تسليم.
3. الخادم + قاعدة البيانات: المنطقة الموثوقة الوحيدة. لا يصل إليها الطالب مباشرة
   إلا عبر API مُصرح به وسياسات RLS.

## 5. تدفق البيانات الحرجة (مثال: تسليم امتحان)

```
طالب -> POST /attempts/{id}/submit (Idempotency-Key)
  -> الخادم: تحقق الجلسة + الدور + ملكية المحاولة + حالة الامتحان + انتهاء الوقت (ساعة الخادم)
  -> معاملة DB واحدة: تجميد الإجابات + تصحيح موضوعي + إنشاء مهام تصحيح يدوي + إشعار
  -> الرد: ملخص فقط (بدون إجابات نموذجية)
```

## 6. قرارات معمارية ملزمة

- ساعة الوقت المرجعية: ساعة الخادم/قاعدة البيانات فقط (`now()` داخل المعاملة).
- الإجابات النموذجية لا تغادر الخادم أبدا قبل استحقاق العرض (حسب إعداد المراجعة).
- نتائج الامتحانات القديمة: لقطة (Snapshot) لنسخة الأسئلة وقت التسليم، لا مرجع حي.
- الحذف للأشياء المهمة: حذف ناعم (Soft Delete) + استعادة، لا حذف فيزيائي مباشر.
- كل تعديل يدوي على علامة يسجل: من، متى، القديمة، الجديدة، السبب (Audit Log).
